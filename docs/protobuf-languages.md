# Protobuf from TypeScript and C# — what it takes, compared with Python

*Status: findings of an experiment, 2026-11-03. Code and output in
[`experiments/protobuf-languages/`](experiments/protobuf-languages/). TypeScript and Python were
run end to end; for C# the code generation was run and the build was stopped by the sandbox's
network (see [what was not run](#what-was-not-run)). Nothing here changes the application.*

## The question

`backend/proto/sincero/simulation_input.proto` is the source of truth for the input fields
([decision](decisions/input-fields-from-proto.md)). In Python that buys little by itself: the
generated `_pb2` messages cannot be the domain's DTOs (mutable, unhashable, zero-valued, no
place for derived amounts), so a 270-line generator turns the `.proto` into frozen dataclasses;
and no tool turns the `.proto` into the OpenAPI document, so a second generator produces the one
component it can ([openapi.md](openapi.md)). The question was whether another language makes
protobuf a better fit — specifically TypeScript and C# — and how much is needed in each to
use the same `.proto`, unchanged, for the same three jobs: **the DTOs**, **parsing the API's
JSON**, and **the defaults and grouping the custom option carries**.

## What was done

The same `.proto` and the same three jobs in each language, with the contract's `400` bodies
as the test material; Python in the same shape, for a like-for-like comparison:

## Findings

### 1. The DTO problem is Python's, not protobuf's

In TypeScript and C# the generated code **is** the DTO. protobuf-es emits structural types
(`type SimulationInput = Message<"sincero.SimulationInput"> & { listPrice: number; … }`) that
any function accepts; Google.Protobuf emits `partial` classes, so the derived amounts of
`ContractData` go into a second file of the same type without touching generated code. Neither
needs a generator on top of protoc. The Python generator exists because the domain is frozen
dataclasses and the `_pb2` classes cannot play that role.

### 2. proto3's semantic gaps are the same in every language

proto3 has no custom defaults and no `required`, and a plain scalar has *implicit* presence
(`list_price: 0` and "no `list_price`" are the same message). So in every language the
`(sincero.field)` option is still the carrier of defaults and nullability, and a small
`resolve` step still applies them: 35 lines in TypeScript, 45 in C#, and in Python the
generator bakes them into the dataclass — the Python experiment's `resolve()` is the same
35 lines as TypeScript's; the other 235 lines of `gen_dto.py` exist to produce dataclasses, not
to apply defaults. The implicit-presence trap shows up in all three —
the experiments' `resolve` reports `list_price: 0` as "required" (the model rejects 0 anyway,
but it is a semantic the `.proto` cannot state). Marking the required fields `optional` too and
checking presence would fix it at the cost of the proto's readability.

### 3. The contract's strict JSON rules are not met by any proto3 parser

The JSON mapping is a specification, and all three runtimes implement it: strings are accepted
for numbers, `null` on a scalar means "unset" (the contract's `null_not_allowed` case is
undetectable), lowerCamelCase aliases are accepted, there are no API limits, and the quoted
`"NaN"` is the mapping's own spelling of NaN. Each of the contract's `400` bodies, in all three:

| Body | Contract | Python (`ParseDict`, run) | TypeScript (protobuf-es, run) | C# (`JsonParser`, from its source) |
|---|---|---|---|---|
| array as body | `wrong_type` | refused | refused | refused |
| `"440000"` for a number | `wrong_type` | **accepted** | **accepted** | **accepted** |
| `true` for a number | `wrong_type` | **accepted as 1.0** | refused | refused |
| `19.0` for an integer | accepted | accepted | accepted | accepted |
| `19.5` for an integer | `wrong_type` | refused | refused | refused |
| `"19"` for an integer | `wrong_type` | **accepted** | **accepted** | **accepted** |
| unknown key | `unknown_field` | refused | refused | refused |
| `listPrice` (camelCase) | `unknown_field` | **accepted** | **accepted** | **accepted** |
| `months_remaining` missing | `missing_field` | accepted | accepted | accepted |
| `itbi_pct: null` | `null_not_allowed` | **accepted, = unset** | **accepted, = unset** | **accepted, = unset** |
| `"NaN"` | `wrong_type` | **accepted** | **accepted** | **accepted** |
| `months_remaining: 5000` | `out_of_range` | accepted | accepted | accepted |
| `2**31` for an `int32` | `out_of_range` | refused | refused | refused |
| `null` inside `balloon_months` | `null_not_allowed` | refused | refused | refused |
| `"12"` inside `balloon_months` | `wrong_type` | **accepted** | **accepted** | **accepted** |

Two consequences. The hand-written shape layer — the contract's rules 2–7 with their `code`,
`field`, `index` — would have to be written again in any language; switching languages does not
remove it. Or the contract changes: "the body is parsed by the proto3 JSON mapping" is a
legitimate, well-specified rule (Google's own APIs use it), it would make the parser the
validator in all three languages, and it would drop `null_not_allowed`, the camelCase
prohibition and the string-number prohibition from the contract. That is a product decision,
not a language one.

### 4. Validation rules can live in the `.proto` — for TypeScript and Python

With `buf.validate` options, the model's `422` rules are expressed next to the fields
(`list_price > 0`, `1 ≤ months_remaining ≤ 600`, `0 ≤ down_payment_pct ≤ 100`, unique balloon
months ≥ 1) and the cross-field rule as a CEL expression
(`this.fgts_upfront + this.cash_upfront <= this.list_price`), with the messages of the
contract. `@bufbuild/protovalidate` enforces them in TypeScript and `protovalidate` enforces the
same file in Python — both run here, with identical violations, paths and messages
(`experiments/protobuf-languages/typescript/output.txt`, `python/rules-output.txt`). There is
no official runtime for .NET, so C# keeps hand-written validators (or FluentValidation on the
partial classes). Two limits: the rules report all violations at once (the contract wants the
first, in a fixed order — a sort of the result), and the API ceilings (`≤ 600`) and the model's
rules (`≥ 1`) end up in the same place, which the contract keeps apart on purpose.

### 5. OpenAPI from the `.proto`: only one ecosystem does it, and it changes the API

No protoc plugin derives a *resource* API — `{path}` into the payload, `?fields=`, `Location`
headers, the contract's `Error` body — from a data schema, in any language. What exists:

| | Produces REST from the `.proto` | Produces OpenAPI | Condition |
|---|---|---|---|
| ASP.NET Core gRPC JSON transcoding + `Microsoft.AspNetCore.Grpc.Swagger` (C#) | yes | yes, served as Swagger | the API is declared as a proto `service` with `google.api.http` annotations (`get: "/api/simulations/{id}/{path=**}"` is expressible); errors become `google.rpc.Status`, not the contract's body; wire names follow the JSON mapping |
| Connect (`@connectrpc/connect-node`, TypeScript; `connectrpc`, Python — both serve Connect, gRPC and gRPC-Web, no proxy) | RPC over HTTP (`POST /sincero.Simulations/CreateSimulation`; `GET` for idempotent RPCs), not the resource routes | not from the protocol itself; `protoc-gen-connect-openapi` (Go binary, not verified here) generates OpenAPI 3.1 from a Connect service | the API becomes RPC-shaped; the same `.proto` serves both languages — run for Python in [`experiments/protobuf-languages/connect/`](experiments/protobuf-languages/connect/) |
| grpc-gateway (Go) | yes | yes | Go |

So "REST + OpenAPI from protobuf" is real only in C#, only after re-expressing the contract as
a service with HTTP annotations and accepting its error model. For the contract as written, the
OpenAPI document stays hand-written in every language, with the input schemas generated from the
`.proto` as today. If the contract is re-expressed as a Connect service instead, Python and
TypeScript are on equal footing — see
[`decisions/api-protocol-and-language.md`](decisions/api-protocol-and-language.md), which
followed this comparison.

### 6. What a language switch would cost

The model is ~1,500 lines of pure Python pinned by 54 Gherkin scenarios (behave) that drive it
through the JSON view, plus 377 unit tests. A backend in TypeScript or C# means porting the
model and its arithmetic (the scenarios are language-neutral and would carry over — Cucumber.js
or Reqnroll — but the step definitions and the support library would not), before any protobuf
benefit appears. The protobuf benefits that do appear are the ones in findings 1 and 4, and they
are worth roughly 300 lines of Python.

## What this means for the project

- **The pain that prompted the question is Python-specific but small**: two generators, 460
  lines, tested, already paid for. A language switch removes them and adds a rewrite.
- **The contract's strictness is the real constraint**, not the language. Either keep the
  hand-written shape layer in whatever language, or adopt proto3 JSON semantics in the contract
  and let the parser be the validator everywhere (finding 3). Decide this first; it decides how
  much protobuf can do.
- **Where protobuf pays off without a rewrite**: the front-end. Milestone 6 is React +
  TypeScript, and the TypeScript experiment shows that six lines of `buf.gen.yaml` turn the
  backend's `.proto` into the form's types, defaults and grouping (`getOption`), with
  `protovalidate` for client-side checks — the language-neutral schema the `.proto` was adopted
  for, realised where it matters.
- **Addendum** ([decision](decisions/api-protocol-and-language.md)): with the API re-expressed
  as a Connect service, Python serves the TypeScript front-end directly (`connectrpc` speaks
  Connect, gRPC and gRPC-Web), so the "REST-shaped contract" assumption behind finding 5 no
  longer constrains the choice; the recommendation there is to keep Python.
- **If a rewrite is wanted for other reasons**: TypeScript is the lower-friction choice for this
  `.proto` (generated types are the DTOs, one generated module shared by backend and front-end,
  `protovalidate` available, fastest parse); C# is the only choice that can also produce the
  REST surface and its OpenAPI from the `.proto`, at the price of re-shaping the contract as a
  gRPC service with HTTP annotations. Neither removes the `resolve` step or the choice in
  finding 3.

## What was not run

The sandbox resolves a handful of package hosts (PyPI, npm, Maven Central, the Ubuntu archive);
NuGet and GitHub are not among them. The .NET 8 SDK was installed from the Ubuntu archive and
`dotnet restore` fails at `NU1301` on `api.nuget.org`; `Google.Protobuf` exists nowhere else.
The C# code was generated with the official `protoc` 3.21 from Maven Central (`Grpc.Tools`
would do it at build), and the program and tests are written against `Google.Protobuf` 3.29's
documented API. The C# column of the table in finding 3 is what its `JsonParser` source
specifies, not an observation; the TypeScript and Python columns are observations, saved as
`output.txt` in each directory.
